# 八人协作与十二天计划

现有原型已经可以作为集成基线。建议优先完善分析设计、数据来源和验收证据，再按时间选择升级功能。不要八个人同时改同一个主文件。

## 1. 分工与交付

| 成员 | 主责 | 主要文件/资源 | 可验收交付 |
|---|---|---|---|
| 1 | 项目负责人、架构、集成 | server.py、API.md | 接口冻结、统一启动、合并审核、架构与部署图 |
| 2 | 仿真环境与 SUMO | tools/export_sumo.py、新建适配器 | SUMO 独立场景可运行；有余力再接 TraCI |
| 3 | 传感器与路况 | 从 simulation.py 拆出观测和路况模块 | 时戳、超时、故障恢复；路况输入说明 |
| 4 | 路径推荐 | app/network.py | 加权目标解释、路况重规划、路线对比实验 |
| 5 | 用户行为分析 | app/behavior.py | 特征和规则说明、样本数据来源；可选 CSV 导入 |
| 6 | 自动响应模型 | 从 simulation.py 拆出策略模块 | 状态图、决策优先级、制动/换道/降级测试 |
| 7 | 前端交互 | static/ | 页面完善、数据单位核对、截图和演示操作 |
| 8 | 测试与文档统稿 | tests/、docs/ | 需求追踪、测试结果、报告统稿、PPT 和答辩脚本 |

第 3、6 人先与负责人约定拆分接口，再修改策略相关代码。每人完成自己模块对应的用例、设计说明和测试；第 8 人负责一致性，不承担代写所有章节。

## 2. 后续十二天安排

| 天数 | 工作 | 完成标准 |
|---|---|---|
| 第 1 天 | 全员运行原型、核对教师要求、确认范围 | 每人能启动；功能清单和报告模板确定 |
| 第 2 天 | 冻结接口，拆分观测、策略和引擎边界 | 合并后现有测试仍通过 |
| 第 3～4 天 | 分模块完善；成员 2 尝试安装和运行 SUMO | 合成数据、规则和实现边界有文档；SUMO 可独立演示或明确回退 |
| 第 5 天 | 全链路集成 | 七个场景均可重复运行 |
| 第 6～7 天 | 完成必要增强：数据导入、实验指标或 SUMO 适配 | 每个增强都有演示或测试证据 |
| 第 8 天 | 功能冻结 | 停止加入新框架与新算法 |
| 第 9～10 天 | 测试、图表、报告与代码一致性检查 | 用例—模块—测试可追踪 |
| 第 11 天 | 换机运行、彩排、录像、打包 | 无网络情况下能演示基础版本 |
| 第 12 天 | 缓冲与提交 | 修复阻塞问题，统一版本 |

若只剩 10 天，取消非必要增强，将第 6～7 天并入文档和测试阶段。

## 3. 开发规则

- 以 `driverlab` 作为课程代码仓库，不把 `references/sumo` 或浏览器测试配置一起提交。
- 每项任务使用独立分支；每天至少合并一次可运行版本。
- 合并前执行 `python -m unittest discover -s tests -v`，说明新增或变更的行为。
- 修改 API 先同步 `docs/API.md` 和前端，统一单位与 null 的含义。
- 数据库、截图、运行缓存已在 `.gitignore` 中排除；正式报告需要的截图单独收集。
- 记录开源参考与自己实现的边界。不能把默认仿真器控制、合成标签或静态示意图写成真实算法效果。

## 4. 推荐的增强顺序

1. 教师要求的用例、类图、顺序图、状态图和测试追踪。
2. 将合成人工驾驶样本替换为可导入、可追踪来源的记录；保持规则模型可解释。
3. 保存完整实验配置，支持相同配置重复运行。
4. 增加请求动作、执行动作和输入观测快照，方便复盘。
5. 有余力时接入 SUMO 适配层，并校验内置模型和 SUMO 的差异。

前四项更容易在短周期内稳定交付。是否必须接入 SUMO，应以教师要求和第 4 天的实际运行结果为依据。
